Four words carry the whole CLI. Once they are clear, every command reads the
same way.

| Word | Meaning |
| --- | --- |
| **Client** | The CLI you run: `claude`, `codex`, `commandcode`, `gemini`, `kiro`, `opencode`, `zcode`, `dsh`, `pi`, `omp` |
| **Source** | What powers it: an account (`grok/work`), a gateway (`openrouter-work`), a pool (`pool:gemini`), the opt-in hub (`hub:default`), or a preset (`@work`) |
| **Binding** | A concrete snapshot: this client → this source, plus model roles |
| **Preset** | An editable template (`@name`), created only when you pass `--save` |

The grammar never changes:

```bash
anypick use|run <client> --with <source|@preset>
```

## Clients

A client is a CLI AnyPick knows how to configure. `anypick clients` lists them
along with what it writes for each:

- `claude` — Claude Code (`ANTHROPIC_*` variables; isolated temp home on `run`)
- `codex` — Codex CLI
- `gemini` — Gemini CLI (`GEMINI_API_KEY`, `GEMINI_MODEL`)
- `kiro` — Kiro
- `opencode` — OpenCode (an `anypick-managed` provider in `opencode.json`)
- `workbuddy` — WorkBuddy AI / CodeBuddy subscription accounts, serving the
  clients above through the built-in proxy. The WorkBuddy *app* itself uses
  its own login directly, and switching the app between saved accounts
  restores its session file natively.
- `zcode` — ZCode (an `anypick` provider in `~/.zcode/cli/config.json` and/or
  `~/.zcode/v2/config.json`)
- `dsh` — DeepSeek Harness (a Cordis-based coding CLI; AnyPick stores the proxy
  key in `~/.dsh/.env`, points `llm-deepseek.baseURL` at the managed proxy in
  `~/.dsh/settings.yaml`, and pins the selected default model and the source's
  model catalog there, so the harness can ride any upstream)
- `commandcode` — Command Code (an OpenAI-compatible BYOK provider in
  `~/.commandcode/providers.json`, with its proxy credential in `auth.json`)
- `pi` — Pi (an `anypick` provider in `~/.pi/agent/models.json` with the
  proxy base URL, plus the default provider/model selection in
  `~/.pi/agent/settings.json`; `~/.pi/agent/auth.json` stays Pi-managed)
- `omp` — Omp (an `anypick` provider in `~/.omp/agent/models.yml` with the
  proxy base URL; the default model stays the user's pick in omp's own UI,
  and `~/.omp/agent/agent.db` credentials are never touched)

Each client has an isolation manifest describing which files and variables
belong to it, which is what makes `anypick reset <client>` and rollback exact
rather than best-effort.

<Aside type="caution" title="ZCode: the desktop app keeps its own model selection">
ZCode stores its chosen model outside `config.json` — the desktop app reads it
from `~/.zcode/v2/setting.json`, which AnyPick does not own. AnyPick writes the
`anypick` provider and, for the CLI config, points `model.main` at it. In the
desktop app the provider is only *registered*: pick **AnyPick** in ZCode's own
model picker once and it stays routed until you `anypick reset zcode`.
</Aside>

<Aside type="note" title="Which clients cross providers">
`claude`, `codex`, `opencode`, `zcode`, `dsh`, `commandcode`, `pi` and `omp`
can be bound to
a source from a different provider — that is what the proxies exist for, and
the exact matrix is enforced by `internal/transport/adapter_test.go`. `gemini`
and `kiro` only accept their own provider's login, so `gemini --with grok/work`
is rejected rather than silently proxied. The `workbuddy` app uses its own
login directly; `workbuddy` *accounts*
still serve the clients above through the proxy, and switching the app
between saved accounts works natively via its session file.
</Aside>

That list is about *binding*. Switching which account is live is broader,
because AnyPick writes the tool's own credential file rather than something only
it understands — so anything else reading that file follows. `claude` covers the
Claude Code CLI and its IDE extensions, and a `gemini` login may be the Gemini
CLI's OAuth or Antigravity's.

<Aside type="caution" title="The Codex desktop app keeps its own session">
AnyPick can back up and restore `~/.codex/auth.json`, which is what the Codex
CLI reads. The desktop app tracks its signed-in ChatGPT account separately, so it
does not follow a switch. AnyPick detects that disagreement and suppresses the
quota readout instead of attributing one account's usage to another.
</Aside>

## Sources

A source is anything that can answer model requests.

**Accounts** are native logins that some other tool created — a Codex
`auth.json`, a Grok credential, a Gemini OAuth token. AnyPick snapshots them so
several can coexist, and restores the one you selected when you activate a
binding. See [Accounts](/docs/guides/accounts).

**Gateways** are API profiles you configure yourself: an endpoint, a key, and
optionally a model catalog. Nothing to log into. See
[Gateways](/docs/guides/gateways).

**Pools** are an opt-in grouping of several accounts of one provider behind a
single port, for failover. See [Proxies](/docs/guides/proxies#multi-account-pools).

**Proxy Hub** is a separate opt-in endpoint that can expose several saved
accounts behind one local address and route by model (`hub:default`). See
[Proxies](/docs/guides/proxies#proxy-hub-opt-in).

They are interchangeable at the `--with` boundary. A client neither knows nor
cares which kind it got.

## Bindings

A binding is a **snapshot**, not a reference. When you run:

```bash
anypick use claude --with grok/work
```

AnyPick resolves the source, picks model defaults, plans the activation steps,
and records the result. Later edits to the account or preset do not silently
rewrite that binding — which is the point. What ran yesterday still runs today.

There are three scopes, checked in this order when you `run`:

1. **Ephemeral** — `run --with <source>` applies for that launch only
2. **Project** — `anypick link` writes a binding scoped to the current directory
3. **Global** — `anypick use` writes the default

```
use   = set the global default (persistent)
run   = launch with the effective binding (ephemeral; never rewrites defaults)
link  = set a project-local binding
```

Inspect what is in effect with `anypick current`, optionally narrowed to one
client.

## Presets

A preset is the one editable thing. It is a named template you can reuse and
revise:

```bash
anypick use claude --with grok/work --save work-stack
anypick use claude --with @work-stack
anypick preset show work-stack
```

There is no in-place preset editor: create a new snapshot with `use … --save`,
or remove the old one with `preset remove`. Editing a preset would not rewrite
bindings that were created from it anyway, because those are snapshots.

<Aside type="note" title="Why snapshots">
The alternative — bindings that follow their source live — means a change in one
place quietly changes what every client launches. AnyPick makes re-activation
explicit instead.
</Aside>

## Activation

Turning a binding into a working client is a planned operation, not a series of
side effects. AnyPick builds a step list, records mutating steps in an operation
journal with backup paths, then executes. If a step fails, prior state is
restored — client config, native auth, and any proxy it started.

`--dry-run` prints the plan without writing. `--trace` names the steps as they
run, without secrets.

## Non-interactive behavior

AnyPick never prompts when there is no TTY, and never guesses a source.
`use <client>` requires `--with`; without it the command exits `2`. This
makes it safe in CI and in scripts. `--no-input` refuses prompts even on a
TTY, and `--json` switches command output to one JSON value on stdout.
